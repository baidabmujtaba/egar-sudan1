# Architecture rules
- Share approved listing discovery and filtering across browsing pages; this keeps public queries explicit and search consistent without changing approval workflows.
- Store browser favorites as listing identifiers only in device-local storage; no existing server favorites schema is available and private listing data must not be cached there.
- Display structured property attributes only when supplied by the listing schema; missing rooms, bathrooms and amenities must not be inferred from descriptions.
- Scope reference-inspired browsing styles to shared discovery components and page classes; administration, payment forms and approval behavior must retain their existing presentation and logic.
- Emit advertiser-contact analytics directly from existing contact-link handlers through the injected optional Lovable events global; use only categorical properties so contact measurement excludes personal data and support clicks.
- Share discovery category values and illustrations between the category rail and search dialog; navigate out of kind-specific browsing pages when a search selects a different listing kind to avoid intersecting incompatible filters.
- Use managed Lovable social auth from shared provider buttons and a public callback that verifies the user before restoring a sanitized same-origin destination; keep profile creation and existing roles intact and exclude OAuth broker paths from PWA navigation caching.
- Fetch public listing details with explicit display/contact columns and an approved-status filter for anonymous visitors; never include payment receipts in public reads, and retain authenticated submission and existing owner/admin review rules.
- Render the fixed submission action only on public browsing/detail routes and link to the existing protected property form; this keeps the call to action visible without bypassing account requirements or covering administration/forms.
- Keep full payment settings admin-only in database policies and load the single current payment instruction through an authenticated, fixed-column RPC after sign-in resolves; this preserves submitter payments without exposing all settings or changing admin-only writes.
